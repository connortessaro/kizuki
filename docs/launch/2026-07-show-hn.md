**Title (exact):**

Show HN: Kizuki – an intelligence layer your AI agent plugs into (local-first, Apache-2.0)

---

## Post body

I spend my day across meetings, Slack threads, and a ticket board that never
stops moving. I already lean on an AI agent for most of my work, but every new
chat started from zero: it had no idea what shipped yesterday, which decision got
reversed, or who was still waiting on me. I kept re-pasting the same background,
and things fell through the cracks anyway. Kizuki is what I built to stop doing
that.

It keeps a local, git-tracked markdown vault sorted by person, project, and team,
backed by append-only JSONL ledgers for signals and captured notes. Your existing
agent plugs in over MCP and does the reading and reasoning; a deterministic JS
layer is the only thing that writes files. The model returns a structured JSON
payload, JS validates it and splices only a managed section, so re-runs are
idempotent and hand-written notes are never clobbered. The goal is to answer the
questions raw search can't: "What changed? What matters now? What conflicts with
prior understanding? What information is missing?"

Install for Claude Code is one line:

    claude mcp add kizuki -- npx -y kizuki mcp

The same `npx -y kizuki mcp` command works with Cursor and Codex; you drop it into
their MCP config in the shape each expects.

Ground rules I hold to: it observes and advises, and never sends a message or
takes an action. You decide what to do with what it surfaces. Everything runs on
your machine, the vault is gitignored, and nothing leaves unless you push it
somewhere yourself. Apache-2.0, and the core has zero runtime dependencies (Node
built-ins only).

What it is not: not a memory database, not enterprise search, not another agent
runtime. Those categories already have strong products. This is the understanding
layer that sits under whichever agent you use, so they share one picture instead
of each rebuilding it from scratch.

- Repo: https://github.com/connortessaro/kizuki
- Demo (synthetic data, no real work data): https://demo.kizuki.dev
- Site: https://kizuki.dev

There's also a small paid founding cohort for people who'd rather have it set up
and run for them, at https://kizuki.dev.

What I'd love feedback on: is MCP-first the right way to package this, or should
the CLI be the front door? Is the strict no-autonomy stance a genuine feature or
just a nag you'd want to switch off? And which sources beyond
Slack/GitHub/Jira/transcripts would actually earn a place in your vault?

## First-4-hours comment prep

**1. Privacy theater? You call it "local-first" but you're piping my work data
through an LLM.**
Fair, and worth being precise about. The reasoning runs in whatever agent or
model you configure; if that's a hosted API, the text of that call goes there, and
I'm not going to dress that up. What stays local is the durable state: the vault,
the append-only ledgers, and the capture daemon (loopback-only, bearer-token auth)
all live on your machine and are gitignored. Want nothing to leave at all? Point
it at a local or self-hosted OpenAI-compatible model. The claim is about where
state lives and who ships it, not that no model ever reads your text.

**2. Why not just grep the files / ripgrep my notes?**
Grep answers "where does this string appear," not "what changed since yesterday,
what conflicts with Tuesday's decision, who's now blocked." Those need something
to have read the activity, connected it to the right people and projects, and
written down the interpretation with a receipt. Grep is actually part of it: the
vault is plain markdown you can grep, and the MCP `search` tool is substring
search. The value is the maintained analysis, not the lookup.

**3. LLM cost. Isn't re-analyzing everything on every sync expensive?**
It can be, and I won't pretend runs are free. Two things bound it: you scope syncs
(one person, one project, one source at a time), and the deterministic layer only
rewrites a managed section, so unchanged files don't churn. You bring your own
agent and model, so the bill is yours to control and a cheaper model for routine
syncs is fine. At large work-data volumes this is a real consideration, not a
solved problem.

**4. Another AI wrapper / another MCP memory server.**
Reasonable prior given how many exist. The difference I'd point to is that the LLM
never writes the store. It returns a validated JSON payload and plain JS does the
writing, which is what makes re-runs idempotent and keeps your hand-edits safe;
most "let the agent remember things" setups let the model mutate state directly.
Whether that boundary is worth a separate tool is exactly what I'm hoping HN tells
me.

**5. What's actually novel here?**
Honestly, no single piece is. Markdown vaults, MCP servers, append-only logs, and
LLM extraction all exist. The bet is the combination: one deterministic,
evidence-backed understanding layer that multiple agents share, that preserves
uncertainty (a hypothesis stays a hypothesis until there's a source receipt), and
that refuses to act. If that combination isn't useful, the project isn't.

**6. Show me a real catch.**
The one that made me build it: an agent was about to draft an update calling a
dependency "on track," pulled from a note that was actually an unconfirmed
hypothesis, while a newer transcript said the owning team had slipped. `kizuki
check` flagged the contradiction against the vault before anything went out. I
record these deliberately with `kizuki catch`, because catches, acted signals, and
prevented mistakes are the only honest measure of whether this earns its place,
not memory count or token spend. The sample is still small; that's the current
risk, and I'd rather say so than fake a metric.
